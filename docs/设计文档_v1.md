## 1. 需求梳理与边界确认

### 1.1 这个工具「做什么」

| 编号  | 能力                | 说明                                                   |
| --- | ----------------- | ---------------------------------------------------- |
| D1  | **只读扫描**手机相册与媒体目录 | 枚举文件、读取元数据、读取字节流。全程对手机侧零写入（反向下载除外）                   |
| D2  | **双通道接入**         | USB（ADB 优先 / MTP 兜底）与 WiFi（局域网）两条通道，规则完全一致           |
| D3  | **原样备份**          | 字节级复制，绝不转码、绝不改 EXIF、绝不重压缩、绝不改尺寸                      |
| D4  | **双端校验**          | 源端 SHA-256 与落盘端 SHA-256 比对，只有一致才标记「已验证」              |
| D5  | **双层归档**          | 按拍摄时间的归档树 + 按手机原始路径的镜像树                              |
| D6  | **增量与秒传**         | 已备份内容不重复传、不重复存                                       |
| D7  | **清理清单**          | 生成"可放心删/建议保留/缓存可清/暂不能删"四档清单，导出 CSV + TXT             |
| D8  | **反向下载**          | 把电脑上的照片推回手机（USB: `DCIM/Restored/`；WiFi: 单张 + 批量 zip） |
| D9  | **断点续传与崩溃恢复**     | 断电/强杀后重启，精确从断点继续，不重复劳动                               |
| D10 | **索引可搬迁**         | 整个备份文件夹随意移动、改名、换盘符，索引仍然有效                            |

### 1.2 这个工具「绝不做什么」

| 编号 | 禁止项                                     | 理由                                     |
| -- | --------------------------------------- | -------------------------------------- |
| N1 | **绝不自动删除手机上的任何文件**                      | 不可协商的安全底线。工具只输出"建议清单"，删除动作 100% 由你手动完成 |
| N2 | 绝不上传任何数据到互联网                            | 全本地运行，仅局域网内部通信                         |
| N3 | 不修改手机端任何文件（含 `.nomedia`、EXIF、时间戳）       | 保证手机侧只读                                |
| N4 | 不调用任何 AI / 大模型 API                      | 零 API 费用、零外部依赖                         |
| N5 | 不写注册表、不写 `%AppData%`、不写 `%ProgramData%` | 纯绿色，卸载 = 删除文件夹                         |
| N6 | 不要求管理员权限                                | 目标电脑普通用户即可运行                           |
| N7 | 不在压缩包内直接运行                              | 必须先解压（详见 10.6）                         |

### 1.3 我识别到的隐含需求（你可能没明说，但我认为必须做）

| 编号  | 隐含需求           | 我的处理                                     |
| --- | -------------- | ---------------------------------------- |
| I1  | **"可信"优先于"快"** | 校验失败的文件主动拦截，宁慢勿错；默认开启写后二次读校验（可关）         |
| I2  | **可解释性**       | 每个文件都要能回答"为什么它被判定为可放心删"                  |
| I3  | **可中断**        | 100GB 任务必须能随时 Ctrl+C，下次继续                |
| I4  | **无副作用试运行**    | 提供 `--dry-run`：只扫描、只出报告、不落盘，先看清单再决定      |
| I5  | **手机侧定位能力**    | 清理清单必须同时给出**手机原始路径**，否则你在手机相册里找不到对应文件    |
| I6  | **多设备支持**      | 镜像树按设备隔离，索引记录 `device_id`，避免两台手机同名文件互相覆盖 |
| I7  | **空间预警**       | 传输前预估总大小并检查目标盘剩余空间，避免跑一半爆盘               |
| I8  | **日志可追溯**      | 每次任务一个日志文件，失败文件单独输出 `失败清单.csv`           |
| I9  | **时间存疑可视化**    | "时间存疑"文件单独成目录并在清单中标注，避免污染正确的时间线          |
| I10 | **ADB 版本隔离**   | 包内自带 ADB，优先于系统 PATH，避免版本冲突（详见 10.2）      |

### 1.4 我认为需要你确认的关键点（详见第 13 节）

已提前列出，最关键的三个是：**① WiFi 通道的能力边界（浏览器无法自动枚举相册）；② MTP 兜底要不要真做；③ 跨盘硬链接降级策略。**

### 2.2 统一通道抽象（双通道一致性的根本保证）

所有规则（扫描范围、时间解析、哈希、去重、归档、清理分档）**全部在领域层**，通道层只负责"枚举文件"和"读字节"，不包含任何业务规则。这样 USB 和 WiFi 走的是**同一套引擎**。

```python
# channels/base.py（伪代码，非最终实现）
class ContentSource(Protocol):
    def probe(self) -> DeviceInfo: ...          # 设备型号/Android 版本/序列号
    def list_files(self, roots: list[str]) -> Iterator[RemoteFile]: ...
    def stat(self, path: str) -> RemoteFile: ...
    def open_stream(self, path: str, offset: int = 0) -> BinaryIO: ...
    def read_range(self, path: str, offset: int, size: int) -> bytes: ...
    def remote_sha256(self, path: str) -> str | None: ...   # 支持则返回，不支持返回 None
    def capabilities(self) -> Capabilities: ...  # 决定能否秒传/能否断点续传
```

| 能力             | ADB             | MTP 兜底     | WiFi 浏览器     | ADB over WiFi |
| -------------- | --------------- | ---------- | ------------ | ------------- |
| 自动枚举全相册        | ✅               | ✅（慢）       | ❌ 需手动选择      | ✅             |
| 源端 SHA-256（秒传） | ✅ `sha256sum`   | ❌          | ⚠️ 需 WASM 分块 | ✅             |
| 任意偏移读取（断点续传）   | ✅ `exec-out dd` | ❌          | ✅ 分片         | ✅             |
| 读取速度           | 快               | 慢（3–10× 慢） | 受 WiFi 带宽限制  | 受 WiFi 带宽限制   |
| 前置条件           | 开 USB 调试 + 授权   | 选"文件传输"模式  | 同网段          | 先 USB 授权一次    |

> **能力降级原则**：通道不支持的能力自动降级（如 MTP 无源端哈希 → 关闭秒传，改为"传输后本地全量校验"），但**校验强度不降级**：最终一律以电脑端落盘 SHA-256 为准。

### 2.3 数据流全链路图

```
[手机文件被枚举]
        │
        ▼
① 扫描过滤  scanner.py
   ├─ 根目录白名单：DCIM / Pictures / Movies / Download（+ 用户勾选 Android/data）
   ├─ 目录黑名单：.thumbnails / .cache / *.tmp / App 缓存目录
   └─ 扩展名白名单：jpg/jpeg/png/gif/webp/bmp/heic/mp4/mov/3gp/mkv/avi...
        │
        ▼
② 元数据采集  stat()
   路径 / 大小 / mtime / 扩展名 / App 归属标签
        │
        ▼
③ 时间解析  times.py
   EXIF DateTimeOriginal → 视频容器 mvhd creation_time → 文件名时间串 → mtime(存疑)
   输出：taken_at + taken_at_source + time_confidence
        │
        ▼
④ 源端哈希  hashutil.py / channel.remote_sha256()
   分块（8MB）流式 SHA-256，内存占用恒定
        │
        ▼
⑤ 秒传判定  dedup.py
   查索引：sha256 已存在且 verified=1 ?
   ├─ 是 → 秒传：只登记 instances + storage 映射，不传输   ────┐
   └─ 否 → 进入传输                                            │
        │                                                     │
        ▼                                                     │
⑥ 传输  channels/*                                             │
   分片写入  <备份根>/.photobak/tmp/<job_id>.part               │
   每片记录 bytes_done → 支持断点续传                           │
        │                                                     │
        ▼                                                     │
⑦ 落盘后本地全量 SHA-256  verify.py                            │
   与源端哈希比对                                               │
   ├─ 不一致 → 删除 .part，重试（指数退避，最多 3 次）           │
   │            └─ 仍失败 → 标记 failed，写入失败清单，拦截 ◀────┤
   └─ 一致 → 继续                                              │
        │                                                     │
        ▼                                                     │
⑧ (可选) 写后二次读校验                                        │
   重新读取落盘文件并哈希，防硬盘静默损坏（默认对 ≥100MB 开启） │
        │                                                     │
        ▼                                                     │
⑨ 原子落地 + fsync                                            │
   os.replace(.part → 最终路径)，父目录 fsync                    │
        │                                                     │
        ▼                                                     │
⑩ 建立镜像树链接  archive.py                                   │
   优先 os.link（硬链接）；失败降级复制；记录 link_type         │
        │                                                     │
        ▼                                                     │
⑪ 写索引（事务）  db.py                                        │
   files.verified=1 + storage + instances  ← 顺序不可颠倒 ◀────┘
        │
        ▼
⑫ 标记为「已验证」→ 具备进入清理清单的资格
        │
        ▼
⑬ 任务结束 → 生成四档清理清单 CSV/TXT
```

> **顺序铁律**：**先落盘并 fsync，再写索引**。绝不允许出现"索引说有、文件不存在"。反向的"文件存在但索引没有"是安全的（doctor 可补录）。

### 2.4 SQLite 索引库完整表结构

数据库文件：`<备份根>/.photobak/index.db`（随备份文件夹一起搬动）。

```sql
PRAGMA journal_mode = WAL;      -- 崩溃安全，断电不易损坏
PRAGMA synchronous = FULL;      -- 数据安全优先于写入速度
PRAGMA foreign_keys = ON;

-- ① 内容主表：以 SHA-256 为唯一身份，一个内容一行
CREATE TABLE files (
    id                INTEGER PRIMARY KEY AUTOINCREMENT,
    sha256            TEXT    NOT NULL UNIQUE,        -- 内容唯一标识（全等去重的唯一依据）
    size              INTEGER NOT NULL,               -- 字节数
    kind              TEXT    NOT NULL,               -- image / video / other
    ext               TEXT    NOT NULL,               -- 小写扩展名，不含点
    taken_at          TEXT,                           -- 解析出的拍摄时间 ISO8601（本地无时区）
    taken_at_source   TEXT,                           -- exif / video_mvhd / filename / mtime / unknown
    time_confidence   INTEGER NOT NULL DEFAULT 0,     -- 3=EXIF确定 2=容器/文件名 1=mtime 0=未知
    is_time_uncertain INTEGER NOT NULL DEFAULT 0,     -- 1 = 时间存疑（来源 mtime）
    verified          INTEGER NOT NULL DEFAULT 0,     -- 1 = 双端校验通过
    verified_at       TEXT,
    second_read_ok    INTEGER,                        -- 1/0/NULL(未做)
    first_seen_at     TEXT NOT NULL,
    last_seen_at      TEXT NOT NULL
);
CREATE INDEX idx_files_sha      ON files(sha256);
CREATE INDEX idx_files_taken    ON files(taken_at);
CREATE INDEX idx_files_verified ON files(verified);

-- ② 出现实例：同一内容可能出现在手机多个路径（如相册 + 微信目录各一份）
CREATE TABLE instances (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id       INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    device_id     INTEGER NOT NULL REFERENCES devices(id),
    source_path   TEXT    NOT NULL,     -- 手机上的原始绝对路径
    source_mtime  TEXT,
    app_tag       TEXT,                 -- Camera / WeiXin / QQ / Screenshot / Download / Other
    root_tag      TEXT,                 -- DCIM / Pictures / Movies / Download / Android_data
    last_seen_at  TEXT    NOT NULL,
    is_present    INTEGER NOT NULL DEFAULT 1,  -- 0 = 最近一次扫描未再见到（可能已删）
    UNIQUE(device_id, source_path)
);
CREATE INDEX idx_inst_file   ON instances(file_id);
CREATE INDEX idx_inst_device ON instances(device_id, is_present);

-- ③ 物理落盘位置：相对路径，保证整个备份目录可搬动
CREATE TABLE storage (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    file_id     INTEGER NOT NULL REFERENCES files(id) ON DELETE CASCADE,
    rel_path    TEXT    NOT NULL,        -- 相对 <备份根> 的路径，一律用 '/' 分隔
    tree        TEXT    NOT NULL,        -- archive(时间树) / mirror(镜像树)
    link_type   TEXT    NOT NULL,        -- file / hardlink / copy / symlink
    created_at  TEXT    NOT NULL,
    UNIQUE(tree, rel_path)
);
CREATE INDEX idx_storage_file ON storage(file_id);
CREATE INDEX idx_storage_path ON storage(rel_path);

-- ④ 设备表
CREATE TABLE devices (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    serial          TEXT UNIQUE,         -- ADB 序列号；浏览器通道用指纹
    model           TEXT,
    android_version TEXT,
    display_name    TEXT,                -- 用于镜像树目录名，安全化后
    first_seen_at   TEXT NOT NULL,
    last_seen_at    TEXT NOT NULL
);

-- ⑤ 传输任务（断点续传的关键）
CREATE TABLE transfer_jobs (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id          INTEGER REFERENCES backup_runs(id),
    source_path     TEXT    NOT NULL,
    device_id       INTEGER NOT NULL,
    expected_size   INTEGER NOT NULL,
    expected_sha256 TEXT,                -- 通道不支持源端哈希时为 NULL
    bytes_done      INTEGER NOT NULL DEFAULT 0,
    part_path       TEXT    NOT NULL,    -- 相对 .photobak/tmp/
    status          TEXT    NOT NULL,    -- pending/running/paused/failed/done
    retries         INTEGER NOT NULL DEFAULT 0,
    last_error      TEXT,
    updated_at      TEXT    NOT NULL,
    UNIQUE(device_id, source_path, expected_size)
);

-- ⑥ 任务运行记录
CREATE TABLE backup_runs (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    started_at    TEXT NOT NULL,
    finished_at   TEXT,
    channel       TEXT,                  -- usb_adb / usb_mtp / wifi_http / wifi_adb
    backup_root   TEXT,                  -- 绝对路径（仅用于日志，索引不依赖）
    status        TEXT,                  -- running/done/cancelled/crashed
    total_files   INTEGER DEFAULT 0,
    total_bytes   INTEGER DEFAULT 0,
    ok_count      INTEGER DEFAULT 0,
    skip_count    INTEGER DEFAULT 0,     -- 秒传
    fail_count    INTEGER DEFAULT 0,
    note          TEXT
);

-- ⑦ 失败明细（供"失败清单.csv"和重试）
CREATE TABLE failures (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id      INTEGER REFERENCES backup_runs(id),
    source_path TEXT NOT NULL,
    reason_code TEXT NOT NULL,           -- 见 4.x 错误码
    reason_text TEXT,
    retries     INTEGER DEFAULT 0,
    occurred_at TEXT NOT NULL
);

-- ⑧ 扫描范围快照（可复现"当时按什么规则扫的"）
CREATE TABLE scan_roots (
    id       INTEGER PRIMARY KEY AUTOINCREMENT,
    run_id   INTEGER REFERENCES backup_runs(id),
    root     TEXT NOT NULL,
    included INTEGER NOT NULL,           -- 1 包含 / 0 排除
    pattern  TEXT                        -- 如 'Android/data' 或 '**/.thumbnails'
);

-- ⑨ 键值设置与 schema 版本
CREATE TABLE settings      (key TEXT PRIMARY KEY, value TEXT);
CREATE TABLE schema_meta   (version INTEGER NOT NULL, applied_at TEXT NOT NULL);
```


**表结构对关键场景的支撑说明**

| 场景    | 支撑设计                                                                                |
| ----- | ----------------------------------------------------------------------------------- |
| 增量备份  | `files.sha256` 唯一 + `instances.last_seen_at`；本次扫描未出现的实例置 `is_present=0`             |
| 跨盘迁移  | `storage.rel_path` 全部相对路径，无绝对路径依赖；迁移后 `doctor` 一次即可                                 |
| 去重    | **只认 `files.sha256` 完全相等**。`IMG_x.jpg` 与 `IMG_x_edit.jpg` 哈希不同 → 两条独立记录，绝不误判        |
| 时间存疑  | `time_confidence` + `is_time_uncertain`，归档时进入 `未知时间/` 或 `时间存疑/` 分支                  |
| 秒传    | `SELECT 1 FROM files WHERE sha256=? AND verified=1`                                 |
| 断点续传  | `transfer_jobs.bytes_done` + `.part` 文件；重启后按 `(device_id, source_path, size)` 命中即续传 |
| 索引一致性 | `files`↔`storage` 一对多；`doctor` 双向核对                                                 |

## 3. 关键技术选型论证

### 3.1 USB 通道：ADB 优先 / MTP 兜底

#### 3.1.1 为什么 ADB 优先

| 维度         | ADB                                             | MTP                      |
| ---------- | ----------------------------------------------- | ------------------------ |
| 枚举速度       | 快（`find` 一次返回）                                  | 慢（WPD/Shell COM 逐层枚举）    |
| 源端哈希       | `adb shell sha256sum <path>` 直接拿到 → **支持秒传**    | 拿不到 → 秒传失效               |
| 断点续传       | `adb exec-out dd if=<path> bs=1M skip=<n>` 精确偏移 | 只能整体复制                   |
| 稳定性        | 高（纯字节流）                                         | 中（WPD 驱动/服务易卡死）          |
| 文件名        | 原始字节，可控                                         | COM 层可能二次编码，emoji/特殊字符风险 |
| 前置条件       | 需开 USB 调试并授权                                    | 只需选"文件传输"                |
| 速度（USB2/3） | 20–120 MB/s                                     | 5–30 MB/s                |

**结论**：ADB 是唯一能同时满足「秒传 + 断点续传 + 稳定」的 USB 方案，因此作为**主通道**。

#### 3.1.2 双模式自动探测与降级

```
启动 USB 通道
   │
   ├─ ① 检查包内 adb.exe 是否可执行 ──否──▶ 报错：文件缺失/被杀软隔离（给具体处理办法）
   │
   ├─ ② adb start-server（超时 10s）
   │      └─ 失败（5037 端口被占）──▶ 自动换端口 ADB_SERVER_PORT=5038..5045
   │
   ├─ ③ adb devices -l 解析
   │      ├─ 无设备 ────────────────▶ 提示：换数据线/换 USB 口/装驱动（分场景给方案）
   │      ├─ unauthorized ──────────▶ 提示：解锁手机，点"允许 USB 调试"（可勾选始终允许）
   │      ├─ offline ───────────────▶ 自动 adb kill-server + start-server 重试一次
   │      └─ device ────────────────▶ ✅ 进入 ADB 模式
   │
   └─ ④ ADB 不可用 → 探测 MTP
          ├─ 用 Shell.Application COM 遍历 "此电脑" 下的便携设备
          ├─ 找到设备 → ⚠️ 降级模式：关闭秒传、关闭源端哈希，全量复制 + 落盘后校验
          └─ 找不到 ──▶ 提示三条并列方案：开 USB 调试 / 切"文件传输"模式 / 装厂商 USB 驱动
```

**前置条件对照**

| 模式  | 手机侧                   | 电脑侧                            |
| --- | --------------------- | ------------------------------ |
| ADB | 开发者选项 + USB 调试 + 授权弹窗 | 无（ADB 已内嵌）                     |
| MTP | 连接方式选"传输文件(MTP)"      | Windows 原生 WPD 驱动（Win10/11 自带） |

**MTP 已知失败场景**：WPD 服务卡死需重启 `Windows Portable Devices` 服务；Win7/8 需额外驱动；部分国产 ROM 的 MTP 实现不稳定；传输 >4GB 单文件易失败。

> **⚠️ 待确认（第 13 节 Q2）**：MTP 兜底实现成本较高（COM 编程 + 大量机型适配），建议**先做 ADB，MTP 只做"检测与提示"**，不真正实现复制。请确认。

### 3.2 WiFi 通道

#### 3.2.1 为什么选 FastAPI + uvicorn

| 候选                      | 评价                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------- |
| **FastAPI + uvicorn** ✅ | 原生 async（大文件流式不阻塞）、原生 WebSocket、自动生成 API 文档、`StaticFiles` 直接托管前端、单进程足够、PyInstaller 兼容性已成熟 |
| Flask                   | 同步模型，大文件并发上传易阻塞；WebSocket 需额外 flask-socketio                                              |
| aiohttp                 | 更轻，但生态/可维护性不如 FastAPI                                                                     |
| Django                  | 严重过重，纯属浪费体积                                                                               |
| 纯 `http.server`         | 无法优雅支持分片并发 + WebSocket                                                                    |

**选择理由**：WiFi 上传天然是 IO 密集 + 长连接场景，async 模型最契合；且 FastAPI 的 `UploadFile` 支持流式落盘，不会把 4GB 视频读进内存。

#### 3.2.2 分片上传设计

| 参数   | 取值                                                                        | 理由                                                                 |
| ---- | ------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| 分片大小 | **8 MB**（可配 1–32MB）                                                       | 太小 → HTTP 开销占比高；太大 → 单片失败重传代价大、浏览器内存压力。8MB 在 WiFi 5 下约 1 秒/片，重传成本低 |
| 分片请求 | `POST /api/upload/chunk`（`upload_id`, `index`, `total`, `sha256_prefix?`） | 每片带序号，服务端可乱序接收后按序拼接                                                |
| 并发   | 浏览器端 2–3 个并发分片                                                            | 兼顾吞吐与稳定性（WiFi 波动时并发过高反而更慢）                                         |
| 断点   | `GET /api/upload/status?upload_id=` 返回已收到的分片位图                            | 手机端刷新/断网后可续                                                        |
| 合并   | 全部分片到齐 → 按序合并为 `.part` → 走统一校验闭环                                          | 合并即回到 §2.3 的第 ⑦ 步                                                  |
| 幂等   | 同一 `upload_id` 重复片直接覆盖，不产生重复文件                                            | 网络重试安全                                                             |

#### 3.2.3 ⚠️ 必须让你知道的可行性边界（关键）

**浏览器沙箱不允许网页自动枚举手机相册。** 手机浏览器打开 `http://<电脑IP>:8765` 后，网页**无法**自己遍历 `/DCIM/Camera`，只能：

- 用户手动点 `<input type="file" multiple>` 选文件（适合补充、小批量）；
- 或 `<input type="file" webkitdirectory>` 选目录（Android Chrome 支持度有限、行为不一致）；
- 或使用 File System Access API（Android Chrome 支持不完整）。

**因此 WiFi 通道有两种形态，我建议都做，你选默认：**

| 形态                          | 自动化程度              | 前置条件                                | 建议定位              |
| --------------------------- | ------------------ | ----------------------------------- | ----------------- |
| **A. 纯浏览器上传**（你原始设想的"扫码"）   | 手动选文件              | 手机浏览器打开电脑网页                         | 补充通道：临时传几张、无数据线时用 |
| **B. ADB over WiFi**（推荐做默认） | **全自动**（等同 USB 体验） | 需先 USB 连一次执行 `adb tcpip 5555`，之后可拔线 | 主通道的无线延伸          |

形态 B 的流程：USB 连一次 → 自动 `adb tcpip 5555` → 终端显示二维码/提示（内含 `adb connect <手机IP>:5555` 的地址）→ 拔线后电脑自动重连 → 之后**全自动枚举 + 秒传 + 断点续传**，与 USB 完全一致。

> **⚠️ 待确认（第 13 节 Q1）**：默认走 A 还是 B？还是 A+B 都做（B 为默认、A 为兜底）？我推荐 **A+B 都做，B 为默认**。

#### 3.2.4 WebSocket 进度推送

- 端点：`ws://<ip>:8765/ws/progress?client=<id>`
- 服务端在引擎回调里 `broadcast(json)`，前端用 `onmessage` 更新进度条、当前文件、速度、剩余时间、失败列表
- 心跳 15s（`ping/pong`），检测手机熄屏断连
- 断连后自动重连并 `GET /api/state` 全量同步一次状态（避免丢事件导致 UI 与实际不一致）

#### 3.2.5 局域网可达性

- 多网卡探测：枚举所有 IPv4（排除 127/169.254/虚拟网卡），优先有线 + 私有网段（192.168/10./172.16-31）
- 二维码内容：`http://<最佳IP>:8765/?t=<一次性token>`
- 一次性 token 防止同网段其他设备误操作（局域网内其他机器打开也需 token）
- **AP 隔离检测**：手机扫码打不开时，主动提示"路由器可能开启了 AP 隔离"，并给出排查步骤（见 4.x）

### 3.3 打包方案：为什么必须 PyInstaller **onedir** 而不是 onefile

| 维度           | onedir（✅ 选它）                       | onefile                            |
| ------------ | ---------------------------------- | ---------------------------------- |
| 启动速度         | 快（直接加载）                            | **每次启动解压整个运行时到 `%TEMP%`**，10–40 秒  |
| 杀软误报         | 较低                                 | **显著更高**（自解压行为像"释放器"）              |
| `%TEMP%` 残留  | 无                                  | 崩溃后残留大量 `_MEIxxxx`，且常被清理软件误删导致运行失败 |
| 资源路径         | 稳定（`_internal/`）                   | 每次路径都变（`sys._MEIPASS` 临时目录）        |
| 子进程（adb.exe） | 路径固定，直接调用                          | 需从临时目录提取，容易被杀软拦                    |
| 首启用户体验       | 双击即用                               | 双击后"卡住"几十秒，用户以为坏了                  |
| 磁盘占用         | 稍大（可接受）                            | 稍小                                 |
| 体积对比         | 未压缩约 120–160MB，**zip 后约 80–120MB** | 单文件约 60–90MB                       |

**结论**：本项目第一优先级是"数据安全 + 开箱即用"，onedir 在启动速度、杀软兼容、稳定性上全面胜出；且我们本来就要交付一个**文件夹**（zip 解压后使用），onedir 完全契合交付形态。

### 3.4 前端：为什么"终端 + 本地浏览器"双窗口

| 维度   | 终端（控制台）                 | 本地浏览器                                     |
| ---- | ----------------------- | ----------------------------------------- |
| 擅长的  | 通道探测、二维码、实时日志、进度条、颜色状态灯 | 复杂交互：勾选树、清单表格、排序筛选、CSV 导出、反向下载、图片预览       |
| 不擅长的 | 表格、勾选、多列排版              | 无法在双击 exe 时"自动弹出"，且用户可能没装浏览器（Win 自带 Edge） |
| 依赖   | 零                       | 零（用系统自带 Edge / 默认浏览器）                     |
| 实现成本 | 低                       | 低（纯本地静态资源，无 CDN）                          |

**方案**：启动时终端负责"能立刻看到进展"（探测、扫码、进度、错误），同时自动 `webbrowser.open('http://127.0.0.1:8765')` 打开本地管理页负责"复杂操作"。

**为什么不做纯桌面 GUI（Tkinter/PyQt）**：

- Tkinter 样式老旧、表格能力弱、渲染二维码/富文本麻烦；
- PyQt/PySide 会让打包体积暴涨 80–150MB，且 GPL/商业授权问题；
- 终端 + 网页是**零额外依赖 + 最佳信息密度**的组合，且网页天然支持手机端访问（同一套 UI 手机也能看进度）。

### 6.2 硬链接实现"一份实体、两棵树可见"

```python
# 核心逻辑（伪代码）
src = 归档树最终路径
dst = 镜像树最终路径
try:
    os.link(src, dst)            # 硬链接：同卷 NTFS 支持，零额外空间
    link_type = 'hardlink'
except OSError as e:
    if e.errno in (errno.EXDEV, errno.EPERM, errno.ENOTSUP):
        shutil.copy2(src, dst)   # 降级：复制（占双倍空间）
        link_type = 'copy'
    else:
        raise
```

**硬链接的限制与降级矩阵**

| 场景                | 是否支持硬链接  | 降级方案                                     |
| ----------------- | -------- | ---------------------------------------- |
| 同卷 NTFS（推荐）       | ✅        | —                                        |
| 同卷 ReFS           | ✅        | —                                        |
| **exFAT（外置硬盘常见）** | ❌        | 降级 `copy`（双倍空间），并**主动提示**                |
| **FAT32**         | ❌        | 降级 `copy`，并提示（且 FAT32 单文件 >4GB 不支持 → 见下） |
| 跨卷（两棵树在不同盘）       | ❌（EXDEV） | 降级 `copy`                                |
| 网络盘 SMB           | ⚠️ 部分支持  | 失败即 `copy`                               |

**额外提示**：FAT32 单文件上限 4GB，遇到 >4GB 视频会失败（E403/E305 变体）→ 启动时检测文件系统类型，若是 FAT32 则**提前警告并建议改用 NTFS/exFAT**。

**降级开关**：配置项 `镜像树链接方式=auto|hardlink|copy|off`，`off` 表示不建镜像树（只保留时间归档树，最省空间）。

### 6.3 索引库使用相对路径

- `storage.rel_path` 一律形如 `照片归档/2023/2023-07/2023-07-15/IMG_xxx.jpg`（`/` 分隔）。
- 运行时代码用 `os.path.join(backup_root, rel_path.replace('/', os.sep))` 还原绝对路径。
- **好处**：整个 `<备份根>` 文件夹剪切到另一个盘、改名、换盘符（D:→E:），索引**无需任何修改**即可继续工作。
- 唯一例外：`.photobak/logs` 与 `reports` 中的日志会记录当时的绝对路径，仅作历史参考，不参与逻辑。

### 6.4 配置文件三级降级逻辑

```
读取 <exe目录>/配置.txt 的 `备份根目录=`

   └─ 使用该路径 ✅
```

## 7. 校验闭环设计（核心）

### 7.1 双端 SHA-256 完整流程

```
源端（手机侧）
   ├─ ADB 通道：adb shell sha256sum "<path>"  → 源哈希 S
   ├─ WiFi+ADB：同上
   ├─ MTP：无源端哈希（S = None）
   └─ WiFi 浏览器：手机端 JS 分块计算 → 源哈希 S
        （技术方案：本地打包 hash-wasm，WASM 支持增量 update，内存恒定；
          若关闭此功能则 S = None，退化为"传输后本地校验"）

         │  S
         ▼
服务端预检（秒传）
   SELECT 1 FROM files WHERE sha256 = S AND verified = 1
   ├─ 命中 → 秒传：不传输，仅登记 instances + storage 映射
   └─ 未命中 → 创建 transfer_job，开始传输

         ▼
传输（分片，可断点）
   写入 .photobak/tmp/<job_id>.part
   可选：每片附带 CRC32，快速发现明显的链路错误（不替代 SHA-256）

         ▼
落盘后本地哈希  ← 【校验的最终裁决点】
   对 .part 完整流式计算本地哈希 L
   ├─ S is not None 且 L != S  → 不一致 → E501 重试流程
   └─ L == S 或 S is None       → 通过
        （S is None 时无法双端比对，只能保证"落盘字节 = 传输字节"，
          因此在清单中标记为「仅单向校验」，安全性略低）

         ▼
（可选）写后二次读校验
   重新打开落盘文件，再次流式计算哈希 L2
   ├─ L2 == L → second_read_ok = 1
   └─ L2 != L → second_read_ok = 0 → E504，禁止进入可删清单

         ▼
os.replace(part → 最终路径) + 父目录 fsync
         ▼
写索引（事务）：files.verified = 1
         ▼
✅ 状态「已验证」→ 获得进入「可放心删」清单的资格
```

### 7.2 大文件分块哈希（内存恒定）

- 分块大小：**8 MB**（与上传分片一致，便于复用）
- 实现：`hashlib.sha256()` + `while chunk := f.read(8*1024*1024): h.update(chunk)`
- 内存占用：恒定约 8MB，与文件大小无关 → 4GB/40GB 文件同样安全
- 进度：每处理一块回调一次进度（供进度条与 WebSocket 推送）

### 7.3 秒传机制

- 传输**前**先问服务端："这个哈希你有吗？"
- 命中条件严格：`sha256` 完全相等 **且** `verified=1` **且** 对应落盘文件经 `doctor` 确认存在
- 命中后：不传输，只新增 `instances`（手机路径记录）与 `storage`（若归档路径不同则建链接）
- 收益：微信转存的重复图、同一张图在多个 App 目录各一份 → 只传一次

### 7.4 只有"已验证"才可进入可清理清单

- 硬规则：`files.verified = 1` **且** `second_read_ok != 0` **且** `doctor` 确认文件存在 → 才具备"可放心删"资格
- 校验失败文件：`files.verified = 0` → 归入「暂不能删」，并在失败清单中列出
- 工具主动拦截：生成清单时执行一次"存在性 + 大小"复核，任一不通过即从可删档剔除并降档

### 7.5 索引库自身的一致性保障

| 措施          | 说明                                                      |
| ----------- | ------------------------------------------------------- |
| WAL 模式      | 崩溃/断电不易损坏                                               |
| 写顺序         | 先落盘 + fsync，**后**写索引；绝无"索引有、文件无"                        |
| 事务          | `files` + `storage` + `instances` 在同一事务提交               |
| 自动备份        | 每次任务结束后把 `index.db` 复制到 `.photobak/backup/`，滚动保留 3 份    |
| `doctor` 体检 | 双向核对：① 索引记录 → 文件是否存在、大小是否一致；② 备份根下的媒体文件 → 是否已登记         |
| 修复策略        | 缺失文件 → 标记 `verified=0` 并降档（不删除记录，保留审计）；未登记文件 → 补录（重算哈希） |
| 启动自检        | 每次启动跑轻量 `integrity_check`，发现异常提示运行体检                    |

### 7.6 是否需要写后二次读校验

- **需要，但可配置**。理由：硬盘静默损坏（bit rot）在机械盘/老旧 SSD 上真实存在，而本项目的核心价值就是"放心删"。
- **默认策略**：对 **≥100MB** 的文件开启二次读校验；小文件默认关闭（数量多、收益低、耗时占比高）。
- **配置项**：`二次读校验=auto|always|never`（默认 `auto`）。
- **代价**：`always` 会让总耗时约增加 30–60%（多读一遍盘），但换来最强的数据信心。
- 结论：**默认 auto，建议你首次全量备份时用 `always`**，之后增量备份用 `auto`。

## 8. 清理建议分档规则

### 8.1 四档判定依据

| 档位             | 精确判定条件（全部满足）                                                                                                                           | 含义                                |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------- |
| **① 可放心删**     | ① `files.verified=1` ② `second_read_ok != 0` ③ `doctor` 确认落盘文件存在且大小一致 ④ 该 `instance` 在本次扫描中 `is_present=1` ⑤ 源路径属于"媒体内容目录"（非 App 私有缓存） | 电脑上已有校验通过的完整副本，删手机上的这份安全          |
| **② 建议保留**     | ① `verified=1` 但 ② 该文件在手机上**是唯一实例**且属于 `app_tag=Camera/Screenshot`（原始拍摄物）**且**用户配置 `保留相机原片=1`                                          | 技术上可删，但属原始拍摄素材，建议再确认一次（如已二次备份到云盘） |
| **③ App 缓存可清** | ① 路径命中缓存特征（`.thumbnails`/`cache`/`Android/data` 且用户已勾选包含）**或** `app_tag` 属于纯缓存类 ② 无论是否 verified 均归此档（缓存本身无备份价值）                        | 可清，但删了 App 可能重新生成，无损失             |
| **④ 暂不能删**     | 命中任一：① `verified=0` ② 传输失败/未传 ③ 正在传输 ④ 时间存疑且用户标记需人工确认 ⑤ 零字节文件 ⑥ 二次读校验失败 ⑦ 属于"疑似唯一副本"且未通过校验                                             | **绝对不要删**，先解决备份问题                 |

### 8.2 附加保护规则（防止误删）

1. **唯一副本保护**：若某内容在手机上只有一份、且电脑端 `verified=0` → 强制进第 ④ 档。
2. **同内容多实例**：若哈希在手机上有 N 份、电脑已验证 → N 份**都**进第 ① 档（内容已在电脑）。
3. **时间存疑保护**：`is_time_uncertain=1` 的文件默认进第 ④ 档（除非用户配置 `时间存疑按可删处理=1`），避免时间线错乱导致误判。
4. **黑名单保护**：清单生成时对每条做一次"落盘文件存在性 + 大小"复核，任一不通过立即降档到 ④。

### 8.3 清单呈现与导出

**终端呈现**：分档汇总表（数量 / 总大小 / 占比）+ Top 20 大文件。

**CSV 导出**（UTF-8 with BOM，Excel 可直接打开）：


## 9. 反向下载（电脑→手机）

### 9.1 USB 模式：一键推回

- 目标目录：`/sdcard/DCIM/Restored/`（可配置）
- 命令：`adb push <本地文件> /sdcard/DCIM/Restored/`
- 冲突处理：同名且哈希相同 → 跳过；同名哈希不同 → 追加 `_restored_1` 后缀（**绝不覆盖手机上的原文件**）
- 空间预检：先 `adb shell df /sdcard` 检查手机剩余空间
- 批量：WebUI 勾选多个 → 逐个 push（进度条 + WebSocket 推送）

### 9.2 WiFi 模式

- **单张长按保存**：WebUI 提供 `/api/download/<file_id>` 直链，手机浏览器长按 → 保存图片到相册
- **批量打包 zip**：`POST /api/download/zip`（`file_ids[]`）→ 服务端流式打 zip（`zipfile.ZipFile` + `ZIP_STORED` 不压缩以省 CPU）→ 浏览器下载
  - 大文件包用流式响应，避免内存爆掉
  - 分批建议：单包 ≤ 2GB，超出时前端自动分批并提示

### 9.3 触发安卓媒体库刷新（关键，否则相册看不到）

按 Android 版本分层尝试，全部失败则给出"手动打开文件管理器"提示：

| 优先级 | 方式                                                                                                               | 适用              |
| --- | ---------------------------------------------------------------------------------------------------------------- | --------------- |
| ①   | `adb shell cmd media_scanner scan /sdcard/DCIM/Restored`                                                         | Android 11+（推荐） |
| ②   | `adb shell am broadcast -a android.intent.action.MEDIA_SCANNER_SCAN_FILE -d file:///sdcard/DCIM/Restored/<file>` | 旧版本（单文件）        |
| ③   | `adb shell am broadcast -a android.intent.action.MEDIA_MOUNTED -d file:///sdcard`                                | 兜底（部分 ROM 需权限）  |
| ④   | 提示用户：在手机上用"文件管理器"打开该目录一次                                                                                         | 全部失败时           |

> 注意：`MEDIA_SCANNER_SCAN_FILE` 在 Android 10+ 已被限制，因此以 ① 为主。

### 9.4 安全边界

- 反向下载是**唯一**会写手机的路径，且**只写入新目录** `DCIM/Restored/`，不触碰任何既有文件。
- 提供 `--no-restore` 开关彻底禁用反向下载功能。

### 10.2 包内 ADB 优先（避免与系统 ADB 冲突）

```python
# main.py 启动早期执行
def _prepend_bundled_adb():
    base = getattr(sys, '_MEIPASS', os.path.dirname(os.path.abspath(__file__)))
    # onedir 下资源在 _internal/（PyInstaller 6+），兼容旧版 _MEIPASS
    adb_dir = os.path.join(base, 'adb')
    if not os.path.isdir(adb_dir):
        adb_dir = os.path.join(base, '_internal', 'adb')
    if os.path.isdir(adb_dir):
        os.environ['PATH'] = adb_dir + os.pathsep + os.environ.get('PATH', '')
        return os.path.join(adb_dir, 'adb.exe')
    return 'adb'   # 退化：用系统 PATH 里的
```

**同时**：所有 ADB 调用都使用**绝对路径** `adb.exe`，不依赖 PATH（PATH 只是给子进程环境用的保险）。
